## Original review verdict (before fixes)

The working-tree tutorial uses the cropmodel package namespaces for local weather,
soil and model execution, but it is **not yet a reproducible, fully integrated
consumer**. The published installation contract cannot load the current driver.
The HPC and experiment orchestration paths also have correctness gaps.

This review covers the local tutorial and its interfaces with the local cropmodel
checkout, including configuration, installation, CI, provider dispatch, folder
construction, execution, resume, HPC, analysis and documentation. Both repositories
already contained extensive uncommitted changes. The initial review changed only this report. The subsequent authorized repair
pass is recorded below; no changes have been committed or pushed.

## Findings, ordered by priority

### 1. P1 — The immutable dependency pin cannot run the current drivers

`requirements.txt:3-4`, `setup_renv.R:53`, `renv.lock:769` and both CI workflows
select cropmodel `08dbe37d8a8ccaa2ec7a9707666e87a93d4ab3ac`.
However, `dssat_main_pipeline.py:327` unconditionally imports
`cropmodel_data.spatial_fallback`. That module does not exist at the pin.
`dssat_main_pipeline.R:394` similarly calls the absent exported
`cropmodeldata::fallback_policy_key`. These calls occur even when spatial fallback
is disabled. The input-lock helpers are also newer than the pin.

Reproduction: exported the exact pinned Python source trees using `git archive`
into a temporary directory, placed them first on PYTHONPATH, and loaded the
tutorial with temporary input/output roots. It failed at line 327 with
`ModuleNotFoundError: No module named 'cropmodel_data.spatial_fallback'`.

The local Python installation resolves into the editable sibling checkout, whose
HEAD was `4dd81c1c3636dd26f2b5f801af726bdfdbfcb6d9`, with additional working-tree
changes. Passing local tests therefore do not establish compatibility with the
declared dependency.

Required correction: finish the required shared changes, select an immutable
revision containing them, update every consumer pin together, and test the
consumer against that exact packaged revision without sibling source leakage.

### 2. P1 — HPC reruns merge stale parts from previous jobs

`hpc/dssat_mpi_runner.py:848,876,895,968` reuses the same per-project part directory
and merges every `temp_results_rank_*.csv` it finds. There is no per-job namespace,
current-rank inventory or startup cleanup. Parts retained by `--merge_mode none`,
interrupted runs, or a previous run with more ranks can be included in a later run.

Reproduction: pre-created `temp_results_rank_3.csv` containing point `99999999`,
then ran the actual main path with a mocked single-rank MPI communicator. The
current input contained only point `00000001`. The final result nevertheless
contained point `99999999` from the old part file.

Required correction: isolate part files per invocation and merge only the exact
parts belonging to that invocation; preserve failed staging as an explicit error.

### 3. P1 — HPC can report success when every model run fails

`hpc/dssat_mpi_runner.py:773-778,804-817,968-992` prints failures and converts them
to no rows. It does not reduce failure counts across ranks or exit unsuccessfully
when expected points/treatments are missing. The final merge still creates a CSV.
`hpc/run_dssat_python.slurm` also only prints a warning for a nonzero runner status
and continues without preserving an aggregate failure status.

Reproduction: the single-rank test above had one point without a FileX. It logged
the failure, wrote the result file and returned normally. No real MPI cluster was
needed to reproduce the single-process branch.

Required correction: publish expected/completed/failed accounting, reduce failure
status across ranks and propagate it through the scheduler wrapper. Explicitly
distinguish deliberately partial results from successful completion.

### 4. P1 — HPC can attach stale stress metrics to a fresh model result

`hpc/dssat_mpi_runner.py:705-712` removes only summary, soilorg, soilni and soilwat
CSV files before running DSSAT. The parser also consumes `plantgro.csv` and
`PlantGro.OUT`, which are not cleared. With cleanup disabled, or after an
interruption before cleanup, a new run that omits PlantGro can inherit the old
run's stress values.

Reproduction: seeded an old PlantGro CSV with stress values 0.8, 0.7 and 0.6;
mocked a fresh successful DSSAT invocation that wrote only a new summary. The
orchestrator returned the fresh yield together with those old stress values.

Required correction: clear or isolate every parser input before each treatment,
and test this through the runner. Prefer reusing shared runtime parsing/execution
where feasible instead of maintaining a separate implementation.

### 5. P1 — Experiment reuse bypasses the driver's completion and provenance checks

`run_experiment.R:245-247` returns success solely because the expected CSV exists.
After execution, line 269 again accepts exit status zero plus file existence.
Neither path checks the new `.status.json` or `.manifest.json` contract.

Consequently, a partial scenario is skipped on restart rather than completed.
Changing a template, treatment selection or other scientific input while retaining
the same scenario filename can also reuse stale results without invoking the
driver's provenance checks. This is especially material because local drivers can
publish partial results and return successfully when at least one point succeeds.

Required correction: use completion validation plus scenario identity when reusing
results, and require explicit handling of partial scenarios before aggregation.

### 6. P2 — Experiment orchestration predicts paths independently of the driver

`run_experiment.R:132-158` derives defaults and result paths before merging the
canonical config. It hardcodes `PROJECT_ROOT/results`, defaults grid spacing to
40000 rather than the current canonical 20000, and does not include the driver's
sampling suffix. The actual driver uses `results_root_dir`/`output_root_dir` and
adds sampling identity to its run name.

Thus an experiment using a custom output root, sampling strategy, or a minimal
base configuration can run successfully but be classified as failed, or can
reuse an unrelated old CSV at its predicted path.

Required correction: derive paths from the same resolved configuration and naming
contract as the driver, or have the driver return a machine-readable artifact
location instead of reconstructing it independently.

### 7. P2 — Test source discovery still assumes nonexistent sibling package repos

`tests/test_smoke.py:31-35`, `tests/test_e2e_comprehensive.py:32-33` and
`tests/test_global_sources.py:38` implement `DSSAT_USE_WORKSPACE_SIBLINGS` using
`../cropmodel_data/python` and/or `../cropmodel_runtime/python`. Monorepo sources
are actually in `../cropmodel/packages/<package>/python`.
`tests/test_e2e_comprehensive.R:44` similarly looks for `../cropmodeldata`.

This opt-in can silently leave tests using a different installed package than
the developer intended. In contrast, the cross-language parity helper knows the
monorepo layout, but prefers local sibling sources over its exact-ref CI checkout.
Several parity checks inspect source strings rather than execute both APIs.

Required correction: centralize package discovery, verify/report the imported
source revision, and run clean-install behavioral contracts in CI. Include the
new provider recovery and scenario completion regressions in CI; several are
currently absent from the explicit workflow test lists.

## Integration and context qualifications

- Critical tutorial helpers were untracked at review time, including
  `python_scripts/scenario_completion.py`, `r_scripts/scenario_completion.R` and
  `scripts/install_ci_dependencies.py`. The monorepo also had untracked sampling
  and provenance modules consumed by optional tutorial paths. Updating a pin to
  the existing monorepo HEAD alone would not publish those files. This is a local
  work-in-progress observation, not a request to commit anything automatically.
- HPC is not routed through cropmodel runtime: it has its own batch writer,
  execution loop, result parser and output schema. It lacks the local driver's
  explicit treatment-list option, sampling metadata joins and scenario sidecars.
  Local/HPC interchangeability therefore needs qualification.
- The provider catalog describes the shared package's capabilities, which exceed
  the tutorial's dispatch table. For example, ERA5-Land is mentioned in README
  setup guidance, but `weather_source: ERA5_LAND` has no dispatch branch in the
  tutorial twins. Document package availability separately from supported driver
  configuration values.
- README line 201 says the lock records R 4.6.x; `renv.lock` records 4.5.3 and CI
  selects 4.3. README line 124 suggests scratch staging of point files; the runner
  stages result part files only. Later README HPC text is more accurate.
- `experiment.yml:10-14` still says orchestration rewrites and restores config.yml;
  the implementation now writes private overlays. Its grid-spacing comment says
  40 km beside a 20000 m value. The architecture diagram and calibration inventory
  still mix older sibling-repository terminology with the monorepo layout.
- The historical migration document is explicitly marked historical, so its old
  package names alone are not an active dependency defect.
- The analysis scripts compute ordinary unweighted summaries and sequential
  additive ANOVA sums of squares. They do not account for new sample-area weights,
  repeated-site structure, or missing-combination imbalance. Treat their reported
  factor shares as exploratory, order-dependent summaries, not a general spatial
  attribution method for stratified or incomplete experiments.
- Git emitted `non-monotonic index` warnings for AppleDouble-style `._pack-*.idx`
  files in the tutorial's Git metadata. Status remained readable. No Git metadata
  was changed; this is a checkout hygiene issue separate from model compatibility.
